# 설계 문서

이 문서는 세 부분으로 나뉩니다.

1. **원문 필수 요구사항** — [`README.md`](../README.md)(과제 원문)에서 확인한 내용
2. **자체 설계 결정** — 원문을 해석해 이 프로젝트가 선택한 정책과 설계
3. **미정 사항** — 구현 전에 결정해야 하는 세부 사항

> **구현 현황**: 최소 실행 환경, **대기 등록 API(`POST /api/parties`)**, **상태 조회 API(`GET /api/me`)** 까지 구현했습니다.
> 화면, 폴링, 체크인, 식사 종료 작업은 아직 구현하지 않았습니다.
> "구현됨"으로 표시한 부분은 실제 코드의 결정이고, "초안"으로 표시한 부분은 구현 과정에서 바뀔 수 있습니다.

## 1. 원문 필수 요구사항

원문 README에서 확인한 요구사항입니다. 아래 표현은 원문을 요약한 것이며, 해석은 2장에서 다룹니다.

### 기술 요구사항

| 항목 | 원문 요구사항 |
| --- | --- |
| 실행 | 전체 앱이 로컬에서 `docker compose up`으로 실행되어야 함 |
| 프런트엔드 패턴 | Isomorphic SSR / Pure SSR(상호작용 없음) / Islands 중 하나. **SPA 금지** |
| 프런트엔드 구현 | 의존성 없는 순수 vanilla JS 또는 React v18+ |
| 백엔드 | Ruby on Rails / Node.js(next·nest 제외) / Go(프레임워크 무관) 중 하나 |
| E2E 테스트 | Playwright |
| 데이터베이스 | MongoDB |

### 비즈니스 요구사항

- **식당 정원**: 10석으로 고정
- **식사 시간**: 인원당 3초로 고정 (예: 4명이면 12초)
- **대기 등록**: 이름(Name), 이메일(Email), 인원수(Party size) 세 필드가 있는 단일 폼. 제출 시 대기 등록 API 요청을 보냄
- **체크인**: 대기 중인 팀이 입장할 준비가 되면 앱에 "check in" 버튼을 표시. 클릭하면
  - 해당 팀이 대기열에서 제외되고
  - 사용 가능한 좌석이 인원수만큼 줄고
  - 해당 팀의 식사 카운트다운이 시작됨
- **상태 확인**: 사용자는 **여러 브라우저 세션에 걸쳐** 자신의 대기 상태를 볼 수 있어야 함
- **대기열 관리**: 한 팀의 식사가 끝나면
  - 시스템이 대기열에서 다음 팀을 확인하고
  - 다음 팀의 인원수만큼 좌석이 있으면 그 팀의 앱에 체크인 버튼을 표시하며
  - 좌석이 부족하면 충분해질 때까지 기다림
- **중복 등록**: 한 팀이 대기열에 두 번 나타나면 안 됨
- **동시성**: 두 팀이 동시에 등록하려 해도 식당이 초과 예약되면 안 되며, 각 팀에 최선의 경험을 제공해야 함

### 제출 요구사항

- 공개 GitHub 저장소
- 원문 README를 포함하고, 로컬 설정·실행 방법을 명확히 안내
- 아키텍처 결정에 대한 간단한 설명(README 또는 별도 문서)

## 2. 자체 설계 결정

### 2.1 운영 정책

#### 좌석과 식사 시간

- 테이블 구분 없이 **총 10석**을 하나의 좌석 풀로 관리합니다.
- 식사 시간은 **인원당 3초**입니다. 식사 종료 예정 시각 = 체크인 시각 + 인원수 × 3초.

#### 입장 순서

- **등록 순서대로** 입장합니다.
- 맨 앞 팀이 입장할 만큼 좌석이 없으면 **뒤 팀도 함께 기다립니다.**
  좌석이 남아 있더라도 뒤 팀이 앞 팀을 건너뛰어 입장하지 않습니다.
- 앞 팀이 체크인하면 그다음 팀의 입장 가능 여부를 확인합니다.
- 따라서 "체크인 가능"한 팀은 대기 중인 팀 가운데 맨 앞 팀이며, 그 팀의 인원수가 남은 좌석 수 이하일 때입니다.

#### 체크인하지 않는 팀

- 체크인 제한 시간과 자동 취소는 **구현하지 않습니다.**
- **알려진 한계**: 맨 앞 팀이 체크인 가능 상태에서 체크인하지 않으면 대기열 전체가 막힐 수 있습니다.
  이 한계는 기록만 하고 구현 범위에서는 제외합니다.

#### 팀 식별과 중복 등록

- **이메일**을 팀 대표자의 식별 기준으로 사용합니다.
- 중복 비교 시 이메일의 **앞뒤 공백을 제거하고 대소문자를 통일**합니다.
- 같은 이메일로 **대기 중 · 체크인 가능 · 식사 중**인 팀이 있으면 추가 등록을 막습니다.
- **이용 완료** 후에는 같은 이메일로 새로 등록할 수 있습니다.
- 같은 팀이 **다른 이메일**로 등록하는 경우는 주어진 정보(이름·이메일·인원수)로 식별할 수 없으므로 막지 않습니다.
  원문의 "한 팀이 대기열에 두 번 나타나면 안 됨"은 "같은 이메일의 진행 중인 팀은 하나뿐"으로 해석합니다.

#### 인원수

- 한 팀은 **1~10명의 정수**만 허용합니다. (정원보다 큰 팀은 영원히 입장할 수 없으므로 거부)
- 팀을 나누어 등록하는 기능은 추가하지 않습니다.

### 2.2 상태 복원 (여러 브라우저 세션)

원문의 "여러 브라우저 세션에 걸쳐 상태를 볼 수 있어야 함"을 다음 범위로 해석해 선택했습니다.

**지원 범위**

- **같은 브라우저**에서의 새로고침, 재방문, 브라우저 종료 후 재접속

**방식**

- 등록 시 추측하기 어려운 무작위 식별 토큰을 발급해 **유지되는(persistent) 쿠키**에 보관합니다.
- 서버는 요청의 토큰으로 연결된 팀을 찾아 **최신 상태를 DB에서 조회**합니다.
- DB에는 토큰 원문 대신 **검증용 해시**를 저장하는 방향으로 설계합니다.

**제외 범위**

- 로그인
- 다른 브라우저·다른 기기에서의 복원
- 쿠키 삭제 후 복원

이는 원문을 해석해 선택한 범위이며, 원문이 다른 브라우저·기기 간 복원까지 의도했을 가능성은 남아 있습니다.

### 2.3 화면

SSR로 생성하는 두 화면으로 구성합니다.

#### 등록 화면

- 이름 · 이메일 · 인원수 입력, 등록 버튼
- 입력 오류 안내 (필수값 누락, 이메일 형식, 인원수 범위, 진행 중인 같은 이메일 등)

#### 내 상태 화면

상태에 따라 표시가 바뀝니다.

| 상태 | 표시 |
| --- | --- |
| 대기 중 | 내 앞에 남은 **대기 팀 수** |
| 체크인 가능 | 입장 안내와 **체크인 버튼** |
| 식사 중 | 서버의 **식사 종료 예정 시각**을 기준으로 계산한 남은 시간 |
| 이용 완료 | 완료 안내와 **다시 등록**할 수 있는 경로 |

- 앞 팀 수는 **대기 중인 팀만** 셉니다. 체크인한 팀은 대기열과 앞 팀 수에서 제외합니다.
- **예상 대기 시간은 제공하지 않습니다.** 미응답 팀 자동 취소가 없어 앞 팀의 체크인 지연을 예측할 수 없기 때문입니다.
- 내 상태 화면은 **폴링 방식**으로 자동 갱신합니다.
  - 폴링 간격 **1초는 초기 제안값**이며 최종 확정값이 아닙니다.
- 브라우저에서 버튼을 숨기거나 비활성화하는 것만으로 중복·동시 요청을 막았다고 간주하지 않습니다.
  모든 규칙은 서버와 DB에서 다시 검사합니다.

### 2.4 데이터 설계 (구현됨: 등록에 필요한 부분)

팀별 문서와 식당 문서를 분리합니다. 코드: `internal/store/store.go`

#### 팀 문서 (`parties` 컬렉션)

| 필드 | 내용 | 상태 |
| --- | --- | --- |
| `_id` | ObjectID | 구현됨 |
| `sequence` | 등록 순번(1부터 증가). 입장 순서 판단 기준 | 구현됨 |
| `name`, `email`, `emailNormalized`, `partySize` | 등록 정보. `email`은 앞뒤 공백 제거한 입력값, `emailNormalized`는 공백 제거 + 소문자 | 구현됨 |
| `status` | `waiting`(대기 중) · `dining`(식사 중) · `completed`(완료) | 구현됨 (등록은 `waiting`만 만듦) |
| `tokenHash` | 식별 토큰의 SHA-256 16진수. 토큰 원문은 저장하지 않음 | 구현됨 |
| `createdAt` | 등록 시각 (UTC, 밀리초) | 구현됨 |
| `successorId` | 완료 팀의 쿠키로 재등록해 만든 새 팀의 `_id` (2.5 참고) | 구현됨 |
| `checkedInAt`, `serviceEndsAt` | 체크인 시각, 식사 종료 예정 시각 | 필드만 정의, 체크인 기능에서 채울 예정 |

#### 식당 문서 (`restaurants` 컬렉션, `_id: "default"` 단일 문서)

| 필드 | 내용 |
| --- | --- |
| `capacity` | 정원 10 |
| `seatsInUse` | 사용 중인 좌석 수. 항상 0~10. **등록은 바꾸지 않음** |
| `nextSequence` | 마지막으로 발급한 등록 순번 |

#### 인덱스 (`parties`)

| 이름 | 정의 | 보장하는 조건 |
| --- | --- | --- |
| `emailNormalized_active_unique` | `{emailNormalized: 1}`, unique, partial `{status: {$in: ["waiting", "dining"]}}` | 진행 중인 팀 사이에서 정규화 이메일이 하나뿐. 완료 팀은 인덱스에서 빠지므로 재등록 가능 |
| `tokenHash_unique` | `{tokenHash: 1}`, unique | 토큰 검증값으로 팀이 하나만 조회됨 |
| `sequence_unique` | `{sequence: 1}`, unique | 등록 순번 중복 없음 |
| `sequence_waiting` | `{sequence: 1}`, partial `{status: "waiting"}` | 고유성 보장용이 아닌 **조회용**. 앞 팀 수를 셀 때 대기 중 팀만 범위 조회 |

- `sequence_waiting`을 추가한 근거: 앞 팀 수 조회 조건은 `{status: "waiting", sequence: {$lt: 내 순번}}`입니다.
  기존 `sequence_unique`로도 조회할 수 있지만, 그러면 내 순번 이전의 **모든** 팀(시간이 지날수록 늘어나는 완료 팀 포함)을 훑은 뒤 상태로 걸러야 합니다.
  부분 인덱스는 대기 중 팀만 담으므로 대기열 길이만큼만 읽습니다. 화면이 폴링으로 자주 부르는 조회라 추가했습니다.
  체크인에서 맨 앞 대기 팀을 찾을 때도 같은 인덱스를 쓸 수 있습니다. 실행 계획으로 이 인덱스를 쓰는 것을 확인했습니다(검증 기록 참고).
- `tokenHash_unique`는 조회 API의 쿠키 해석에도 그대로 씁니다.

- partial index 조건에 `$in`을 쓴 근거: MongoDB 8.0 공식 문서(Partial Indexes)는
  `partialFilterExpression`에서 equality, `$exists: true`, `$gt`/`$gte`/`$lt`/`$lte`, `$type`, `$and`, `$or`, `$in`을 지원한다고 명시합니다.
  상태 값과 직접 연결된 조건이라 별도의 "진행 중 이메일" 필드를 동기화할 필요가 없습니다.

#### 스키마 준비 (반복 실행 안전)

- 서버 시작 시 `EnsureSchema`가 인덱스를 만들고(같은 정의가 있으면 변화 없음),
  식당 문서를 `$setOnInsert` upsert로 **없을 때만** 만듭니다. 기존 `seatsInUse`, `nextSequence`는 덮어쓰지 않습니다.
- DB가 잠시 응답하지 않으면 최대 30초 동안 재시도하고, 끝내 실패하면 서버를 시작하지 않습니다.

#### 저장하지 않고 계산하는 값

- **체크인 가능 여부**: 대기 중 + 앞 팀 수 0 + 인원수 ≤ (정원 − 사용 중인 좌석) — `party.CanCheckIn` (구현됨)
- **앞 팀 수**: 나보다 등록 순번이 앞선 대기 중인 팀의 수. 식사 중·완료 팀은 세지 않음 (구현됨)
- **남은 식사 시간**: 식사 종료 예정 시각 − 서버 시각. 서버는 두 값을 함께 돌려주고, 화면이 차이를 계산 (화면은 미구현)

### 2.5 동시 요청과 체크인

#### 체크인 처리

- 체크인 요청 시 서버가 다음을 **다시 확인**합니다.
  - 팀의 현재 상태
  - 대기 순서(맨 앞 팀인지)
  - 빈 좌석 수
- 팀 상태 변경(대기 중 → 식사 중)과 식당 좌석 변경(사용 중 좌석 + 인원수)을 **하나의 MongoDB 트랜잭션**으로 묶습니다.

#### 트랜잭션에 대한 주의

트랜잭션을 사용한다고 자동으로 안전해지지는 않습니다. 다음이 함께 필요합니다.

- **공통 식당 문서 갱신**: 좌석에 영향을 주는 모든 트랜잭션(체크인, 식사 종료)이 같은 식당 문서를 쓰도록 해,
  동시에 진행된 트랜잭션끼리 쓰기 충돌이 나게 만듭니다. 서로 다른 문서만 읽고 쓰면 각자 오래된 값을 근거로
  판단한 결과가 모두 커밋될 수 있습니다.
- **충돌 재시도**: 쓰기 충돌 등 일시적 트랜잭션 오류가 나면 트랜잭션 전체를 다시 실행합니다.
- **재시도 시 조건 재확인**: 재시도할 때 이전 시도에서 읽은 값을 재사용하지 않고, 상태·순서·좌석 조건을 처음부터 다시 확인합니다.
- 좌석 갱신 자체도 조건부로 수행합니다(예: 사용 중 좌석 + 인원수 ≤ 정원일 때만 증가).

#### 지켜야 할 불변 조건

- 사용 중인 좌석은 **항상 0~10석**입니다.
- 좌석 차감과 반환은 **팀별로 각각 한 번만** 반영됩니다.
- **반복 체크인**으로 좌석을 다시 차감하지 않습니다. 이미 체크인된(식사 중인) 팀의 재요청에는 **현재 상태를 반환**합니다.
- **완료된 팀**의 체크인 요청으로 식사를 다시 시작하지 않습니다.

#### 등록 트랜잭션 (구현됨)

코드: `internal/store/register.go`. 순번 발급과 팀 생성은 **하나의 트랜잭션**입니다
(read concern `snapshot`, write concern `majority`).

1. 요청 쿠키의 토큰 해시로 팀을 찾습니다.
   - 진행 중(대기·식사) → 아무것도 쓰지 않고 그 팀을 돌려줍니다. (입력한 이메일·이름·인원수는 무시)
   - 완료 팀이고 이미 이 쿠키로 재등록한 팀(`successorId`)이 진행 중 → 그 팀을 돌려줍니다.
   - 완료 팀이고 아직 재등록하지 않음 → 이번 등록의 **선행 팀**으로 기억합니다.
   - 찾지 못함 → 쿠키가 없는 요청과 같이 처리합니다.
2. 선행 팀이 있으면 그 문서에 `successorId`를 조건부(`status: completed`, `successorId` 없음)로 기록합니다.
3. 식당 문서의 `nextSequence`를 `$inc`로 원자적으로 증가시켜 순번을 받습니다.
4. 새 팀을 `waiting`으로 삽입합니다. 진행 중인 같은 정규화 이메일이 있으면 부분 고유 인덱스가 거부 → 409.
   이때 트랜잭션 전체가 중단되어 2·3단계 변경도 남지 않습니다. 순번도 소모되지 않습니다.

**동시 요청 처리**

| 경우 | 처리 방식 |
| --- | --- |
| 같은 이메일, 쿠키 없음 | 모든 등록이 식당 문서(카운터)를 쓰므로 쓰기 충돌로 직렬화되고, 재시도에서 부분 고유 인덱스가 중복을 거부 → 한 건만 201, 나머지 409 |
| 다른 이메일 | 카운터 `$inc`가 트랜잭션 안에서 원자적이고 `sequence` 고유 인덱스가 있으므로 순번 중복 없음 |
| 같은 완료 쿠키로 동시 재등록 (이메일이 서로 달라도) | 모두 선행 팀 문서에 `successorId`를 쓰려 하므로 쓰기 충돌 → 재시도한 쪽은 1단계에서 이미 만들어진 새 팀을 보고 200(기존 등록)을 돌려줌 → 새 팀은 한 건 |
| 같은 진행 중 쿠키로 반복 | 읽기만 하고 200 |

**재시도와 제한 시간**

- 쓰기 충돌 등 `TransientTransactionError`는 드라이버의 `WithTransaction`이 콜백 전체를 다시 실행합니다.
  콜백은 매 시도에서 쿠키 팀·선행 팀·카운터를 DB에서 다시 읽습니다.
- 재시도를 포함한 트랜잭션 한 건의 전체 시간은 **5초**(`DefaultTxTimeout`)로 제한합니다. 시도 시작 시 제한 시간을 넘겼으면 더 시도하지 않습니다.
- 콜백 안에서는 HTTP 응답·쿠키 발급을 하지 않습니다. 쿠키는 커밋이 끝난 뒤 핸들러에서 발급합니다.
- 새 토큰은 트랜잭션 전에 한 번 만들고, 재시도에서도 같은 해시를 사용합니다. (중단된 시도는 아무것도 남기지 않음)

**DB가 보장하는 조건과 애플리케이션이 처리하는 조건**

| DB가 보장 (인덱스·원자적 연산·트랜잭션) | 애플리케이션이 처리 |
| --- | --- |
| 진행 중 팀 사이 정규화 이메일 고유 (부분 고유 인덱스) | 입력 검증, 이메일 정규화 |
| 등록 순번 고유·원자적 발급 (`$inc` + 고유 인덱스) | 쿠키 토큰 형식 확인과 해시 계산 |
| 토큰 해시 고유 | 쿠키 팀의 상태에 따라 기존 등록 반환 여부 판단 |
| 순번 발급·선행 팀 표시·팀 생성의 원자성 (트랜잭션) | 완료 쿠키 재등록을 한 번만 허용하는 규칙 (DB의 조건부 갱신과 쓰기 충돌로 강제) |
| 완료 쿠키당 재등록 한 건 (선행 팀 문서 조건부 갱신 + 쓰기 충돌) | 중복 키 오류를 409로, 그 밖의 오류를 500으로 변환 |

#### 로컬 MongoDB 구성

- MongoDB 트랜잭션은 replica set(또는 sharded cluster)에서만 동작하므로,
  로컬 Docker Compose 환경도 **replica set으로 구성**해야 합니다.

### 2.6 식사 종료

- **서버 내부의 주기적 작업**이 식사 종료 예정 시각이 지난 팀을 확인합니다.
- 팀 상태 변경(식사 중 → 완료)과 좌석 반환을 **하나의 트랜잭션**으로 묶습니다.
- 이미 완료한 팀은 다시 좌석을 반환하지 않습니다(상태가 식사 중일 때만 완료 처리).
- 브라우저 접속이나 상태 조회 요청이 **없어도** 종료 처리가 동작합니다.
- 서버 재시작 후에는 **DB에 저장된 종료 예정 시각**을 기준으로 처리를 재개합니다.
  메모리의 타이머에 의존하지 않으므로 재시작 중 종료 시각이 지난 팀도 다음 확인에서 처리됩니다.
- **처리 지연**: 주기적으로 확인하므로 실제 완료 처리는 종료 예정 시각보다 최대 "확인 주기 + 처리 시간"만큼 늦을 수 있습니다.
  이 동안 좌석은 아직 반환되지 않은 상태로 보이며, 다음 팀의 체크인 가능 표시도 그만큼 늦어질 수 있습니다.
- 손님용 식사 종료 버튼이나 종료 API는 추가하지 않습니다.

### 2.7 API

| 메서드 | 경로 | 용도 | 상태 |
| --- | --- | --- | --- |
| `POST` | `/api/parties` | 대기 등록 (이용 완료 후 재등록도 같은 경로 사용) | **구현됨** |
| `GET` | `/api/me` | 쿠키의 토큰에 연결된 내 팀의 상태 조회 | **구현됨** |
| `POST` | `/api/me/check-in` | 체크인 | 초안, 미구현 |

- HTML 화면(등록 화면, 내 상태 화면)을 제공하는 경로는 API와 별도로 둡니다. 구체적인 경로는 미정입니다.

#### `POST /api/parties` (구현됨)

요청 본문 (`Content-Type: application/json`, 최대 4KiB):

```json
{ "name": "Kim", "email": "kim@example.com", "partySize": 2 }
```

**입력 검증**

| 필드 | 규칙 |
| --- | --- |
| `name` | 필수 JSON 문자열. 앞뒤 공백 제거 후 빈 값 거부. 최대 100자 |
| `email` | 필수 JSON 문자열. 앞뒤 공백 제거 후 형식 검증, 소문자로 정규화. 최대 254자 |
| `partySize` | 필수 JSON 정수 리터럴. 1~10. 문자열(`"2"`), 소수(`2.5`, `2.0`), 지수(`1e1`), 불리언은 거부 |
| 본문 전체 | JSON 객체 하나. 문법 오류, 알 수 없는 필드, 뒤에 붙은 추가 JSON 값, 크기 초과는 거부 |

- 이메일 형식 기준: `net/mail`로 해석되는 단일 주소이면서 표시 이름이나 꺾쇠괄호(`Kim <a@b.com>`)가 없고,
  도메인에 점(`.`)이 있으며 점으로 시작·끝나지 않아야 합니다. 실제 수신 가능 여부는 확인하지 않습니다.
- 추가로 정한 최소 제한과 근거:
  - 이름 100자, 이메일 254자: 화면 표시와 저장 크기의 상한. 이메일은 RFC 5321 경로 길이 제한을 따름
  - 본문 4KiB: 정상 입력보다 충분히 크며 큰 본문으로 서버 자원을 쓰는 것을 막음
  - 알 수 없는 필드 거부: 필드 이름 오타(`party_size` 등)를 조용히 무시하지 않기 위함
  - JSON이 아닌 Content-Type은 415: CSRF 대응의 일부이자 폼 전송과 구분하기 위함 (2.8)

**처리 순서**

1. CSRF 검사 → 실패 시 **403**
2. Content-Type 확인 → `application/json`이 아니면 **415**
3. 본문 해석과 필드 검증 → 실패 시 **400**.
   DB를 보지 않는 순수 검사이므로 **기존 등록 확인보다 먼저** 수행합니다.
   유효한 쿠키가 있어도 입력이 잘못되면 400입니다.
4. 등록 트랜잭션 (2.5) → 기존 진행 중 등록 **200** / 이메일 중복 **409** / 새 등록 **201**
5. 그 밖의 오류 → **500** (상세는 서버 로그에만)

**응답**

| 상태 | 본문 | 쿠키 |
| --- | --- | --- |
| 201 | `{"result":"created","party":{...}}` | 새 식별 쿠키 발급 (커밋 후) |
| 200 | `{"result":"existing","party":{...}}` — 쿠키가 가리키는 진행 중 팀 | 발급 안 함 |
| 400 | `{"error":{"code":"invalid_input","message":"...","fields":{"name":"...",...}}}` 또는 `code: "invalid_json"` | 발급 안 함 |
| 403 | `{"error":{"code":"forbidden",...}}` | 발급 안 함 |
| 409 | `{"error":{"code":"email_in_use","message":"이 이메일로 진행 중인 등록이 있습니다. 등록했던 브라우저에서 확인해 주세요."}}` — 기존 팀 정보 없음 | 발급 안 함 |
| 415 | `{"error":{"code":"unsupported_media_type",...}}` | 발급 안 함 |
| 500 | `{"error":{"code":"internal_error",...}}` — 내부 상세 없음 | 발급 안 함 |

- `party`에는 최소 정보만 담습니다: `name`, `partySize`, `status`, `registeredAt`.
  이메일, 등록 순번, 토큰·토큰 해시는 담지 않습니다.
- 체크인 가능 여부와 앞 팀 수는 아직 구현하지 않았으므로 **응답에 넣지 않습니다**(임시값 없음).
- 쿠키 없이 이메일만 같은 요청에는 기존 팀의 어떤 정보도 돌려주지 않습니다.

#### `GET /api/me` (구현됨)

식별 쿠키로 내 팀의 현재 상태를 돌려줍니다. 코드: `internal/api/me.go`, `internal/store/status.go`

**응답**

| 상태 | 조건 | 본문 |
| --- | --- | --- |
| 401 | 쿠키 없음, 형식 오류, 연결된 팀 없음 | `{"error":{"code":"not_registered","message":"등록 정보를 확인할 수 없습니다."}}` |
| 200 | 팀을 찾음 (완료 포함) | 아래 상태별 형식 |
| 500 | 내부 오류, 끊어진 successor 참조 등 데이터 불일치 | `{"error":{"code":"internal_error",...}}` — 상세 없음 |

- 모든 응답에 `Cache-Control: no-store` (개인 상태이므로 브라우저·프록시에 캐시하지 않음)
- `Set-Cookie`를 보내지 않습니다. 쿠키를 회전하거나 새 토큰을 발급하지 않습니다.

**상태별 필드 (200)**

| 필드 | waiting | dining | completed |
| --- | --- | --- | --- |
| `party.name`, `party.partySize`, `party.status`, `party.registeredAt` | 포함 | 포함 | 포함 |
| `waiting.aheadCount` — 앞선 대기 중 팀 수 | 포함 | 생략 | 생략 |
| `waiting.canCheckIn` — 체크인 가능 여부(안내) | 포함 | 생략 | 생략 |
| `dining.serviceEndsAt` — 저장된 식사 종료 예정 시각 | 생략 | 포함 | 생략 |
| `dining.serverTime` — 응답 시점의 서버 시각 | 생략 | 포함 | 생략 |

```json
{"party":{"name":"Kim","partySize":2,"status":"waiting","registeredAt":"2026-11-17T01:00:00Z"},
 "waiting":{"aheadCount":1,"canCheckIn":false}}

{"party":{"name":"Kim","partySize":2,"status":"dining","registeredAt":"2026-11-17T01:00:00Z"},
 "dining":{"serviceEndsAt":"2026-11-17T01:05:06Z","serverTime":"2026-11-17T01:05:02Z"}}

{"party":{"name":"Kim","partySize":2,"status":"completed","registeredAt":"2026-11-17T01:00:00Z"}}
```

- 생략은 키 자체가 없다는 뜻입니다. (`null`이나 임시값을 넣지 않음)
- 예상 대기 시간은 제공하지 않습니다. (2.3)
- 토큰, 토큰 해시, 이메일, 등록 순번, `successorId`, `_id`는 반환하지 않습니다.
- 이메일만으로 조회하는 기능은 없습니다.
- `serverTime`을 함께 주는 이유: 화면이 `serviceEndsAt - serverTime`으로 남은 시간을 계산하면 브라우저 시계가 틀려도 영향이 없습니다.

**조회 일관성**

- 쿠키 해석, 앞 팀 수, 좌석 수를 **하나의 읽기 전용 트랜잭션**(read concern `snapshot`)에서 읽습니다.
  모든 읽기가 같은 시점의 데이터를 보므로, 예를 들어 "앞 팀 수는 체크인 전, 좌석은 체크인 후"처럼 섞인 결과가 나오지 않습니다.
- 제한 시간은 **2초**(`DefaultReadTimeout`)입니다. 화면이 폴링으로 자주 부를 조회이므로 쓰기(5초)보다 짧게 두어, DB가 느릴 때 요청이 쌓이지 않게 합니다.
- 조회는 아무것도 쓰지 않습니다. 종료 예정 시각이 지난 식사 중 팀도 그대로 식사 중으로 보입니다. 종료 처리는 식사 종료 작업이 맡습니다. (2.6, 미구현)
- **`canCheckIn`은 조회 시점의 안내일 뿐입니다.** 조회 뒤 다른 팀의 체크인·종료로 상황이 바뀔 수 있으므로,
  체크인 API는 이 값을 믿지 않고 트랜잭션 안에서 순서와 좌석을 반드시 다시 확인해야 합니다. (2.5)

### 2.8 식별 쿠키와 CSRF (구현됨)

#### 토큰

- 32바이트 `crypto/rand` 무작위 값을 base64url(패딩 없음, 43자)로 인코딩합니다.
- DB에는 SHA-256 16진수만 저장합니다. 토큰이 256비트 무작위 값이라 추측이 불가능하므로 느린 비밀번호 해시는 필요 없습니다.
- 형식(길이·인코딩)이 맞지 않는 쿠키는 DB를 조회하지 않고 무시합니다.
- 토큰 원문은 응답 본문과 로그에 쓰지 않습니다.

#### 쿠키 속성

| 속성 | 값 | 이유 |
| --- | --- | --- |
| 이름 | `waitlist_token` | `__Host-` 접두사는 `Secure`를 요구해 로컬 HTTP에서 쓸 수 없으므로 사용하지 않음 |
| `HttpOnly` | 켬 | 페이지 스크립트가 토큰을 읽을 필요가 없음. XSS가 생겨도 토큰 탈취를 막음 |
| `SameSite` | `Lax` | 아래 "SameSite=Lax의 동작" 참고 |
| `Path` | `/` | 화면과 API 모두에서 사용 |
| 유효기간 | `Max-Age` 7일 | 브라우저를 닫았다 열어도 복원(세션 쿠키 아님). 대기·식사 시간보다 충분히 길면서 오래된 토큰이 무기한 남지 않게 함 |
| `Secure` | 환경변수 `COOKIE_SECURE` (기본 `false`) | 로컬은 `http://127.0.0.1`이라 기본값을 끔. **HTTPS 배포에서는 반드시 `true`로 설정** |

- 쿠키는 등록 트랜잭션이 커밋된 뒤에만 발급합니다. 200·4xx·5xx 응답에서는 발급하지 않습니다.

#### SameSite=Lax의 동작

브라우저는 요청이 어디서 시작됐는지에 따라 `Lax` 쿠키를 다음과 같이 보냅니다.

| 요청 | 쿠키 전송 |
| --- | --- |
| 이 사이트 안에서의 요청 (같은 출처의 `fetch`, 폼 제출, 이동) | 보냄 |
| 다른 사이트(cross-site)에서 시작한 **POST** (자동 제출되는 폼, `fetch` 등) | **보내지 않음** |
| 다른 사이트 페이지 안의 하위 요청 (이미지, iframe, `fetch` GET 등) | 보내지 않음 |
| 다른 사이트의 링크를 눌러 이 사이트로 오는 **최상위(top-level) GET 이동** | **보냄** |

- 그래서 외부 링크(메신저, 메일 등)로 들어와도 상태가 복원됩니다. `Strict`는 이 최상위 GET 이동에도 쿠키를 보내지 않아, 처음 화면이 "등록 안 됨"으로 보일 수 있으므로 택하지 않았습니다.
- 최상위 GET 이동에 쿠키가 실려도 안전하려면 **GET으로 상태를 바꾸지 않아야** 합니다. 등록·체크인은 POST로만 둡니다.
- Chrome의 "SameSite를 지정하지 않은 쿠키에 한해 2분간 cross-site 최상위 POST를 허용"하는 예외는, `SameSite=Lax`를 명시한 이 쿠키에는 적용되지 않습니다.
- `SameSite`는 **사이트**(등록 도메인) 단위입니다. 같은 사이트의 다른 출처(예: 같은 도메인의 다른 하위 도메인)에서 온 요청은 막지 않으므로, 아래 CSRF 검사가 따로 필요합니다.

#### 쿠키 발급·유지의 일관성

DB에는 토큰 해시만 있으므로 서버는 이미 발급한 토큰을 다시 보낼 수 없습니다. 그래서 다음 규칙을 지킵니다.

- 새 토큰을 담은 `Set-Cookie`는 **새 팀을 만든 201 응답 하나에만** 붙습니다. 토큰은 그 팀 문서에 해시로 저장된 값과 같습니다.
- 200(기존 등록), 409, 4xx, 5xx 응답은 `Set-Cookie`를 보내지 않으므로, 브라우저에 있는 쿠키를 바꾸지 않습니다.
- 같은 완료 쿠키로 동시에 재등록하면 새 팀과 201 응답은 하나뿐입니다. 나머지 응답은 같은 새 팀을 200으로 돌려주고 쿠키를 건드리지 않습니다.
  따라서 응답이 어떤 순서로 도착해도 브라우저에 최종 저장되는 쿠키는 다음 둘 중 하나입니다.
  - 201 응답이 도착한 경우: 새 팀의 쿠키
  - 201 응답이 유실된 경우: 이전 완료 팀의 쿠키. 이 쿠키도 `successorId`를 통해 새 팀으로 연결되므로 등록 API는 200으로 새 팀을 돌려줍니다.
- 기존 토큰을 다시 만들어 발급(회전)하지 않습니다. 회전하면 동시 요청 중 먼저 도착한 응답의 쿠키가 무효가 될 수 있기 때문입니다.
#### 쿠키 해석 규칙 (등록·조회 공통)

등록 API와 조회 API는 같은 함수(`internal/store/resolve.go`의 `resolveToken`)로 쿠키를 해석합니다.
해석은 각 API의 트랜잭션 안에서 이루어지므로, 해석과 이후 판단이 같은 스냅샷을 봅니다.

| 쿠키 토큰으로 찾은 팀 | 쿠키가 가리키는 팀 | `GET /api/me` | `POST /api/parties` |
| --- | --- | --- | --- |
| 없음 (또는 쿠키 없음·형식 오류) | 없음 | 401 | 쿠키 없는 요청으로 처리 |
| 대기 중·식사 중 | 그 팀 | 200 그 팀 | 200 그 팀 (새 팀 없음) |
| 완료, `successorId` 없음 | 그 팀 | 200 완료 | 이 팀을 선행 팀으로 새 팀 생성 201 |
| 완료, successor 진행 중 | successor | 200 successor | 200 successor (새 팀 없음) |
| 완료, successor도 완료 | successor | 200 successor의 완료 상태 | 쿠키 없는 요청으로 처리 (재등록 권한 없음, 2.9) |
| 완료, `successorId`가 없는 팀을 가리킴 (끊어진 참조) | — | **500** | **500** (새 팀 없음) |

- 연결은 **한 단계만** 따라갑니다. successor의 successor는 보지 않습니다.
- successor까지 완료된 오래된 쿠키는 조회에서 "완료"로 보이고, 등록에서는 재등록 권한이 없습니다.
  두 해석은 같은 뜻입니다: **이 쿠키에는 진행 중인 등록이 없다.** 화면은 완료 안내와 함께 다시 등록하게 할 수 있습니다.
- **끊어진 참조**(successorId가 존재하지 않는 팀을 가리킴)는 정상 흐름에서 생기지 않는 데이터 불일치입니다.
  미등록(401)이나 새 등록 허용으로 숨기면 원인을 놓치므로, 두 API 모두 500을 돌려주고 원인은 서버 로그에만 남깁니다.
  (이전 등록 구현은 이 경우를 쿠키 없는 요청으로 처리했는데, 이번에 조회와 맞춰 500으로 바꿨습니다.)

#### CSRF 대응 (최소 범위)

- `/api/` 아래 모든 요청을 Go 1.25+ 표준 라이브러리 `http.CrossOriginProtection`으로 감쌉니다.
  - 브라우저의 `Sec-Fetch-Site`가 `same-origin` 또는 `none`이 아니면 403
  - `Sec-Fetch-Site`가 없으면 `Origin` 헤더의 호스트가 요청 `Host`와 다를 때 403
  - 두 헤더가 모두 없으면 브라우저가 아닌 요청(curl 등)으로 보고 허용
  - GET/HEAD/OPTIONS는 검사하지 않으므로 상태 변경은 이 메서드로 하지 않습니다.
- 추가 방어: JSON Content-Type 요구(415)와 `SameSite=Lax` 쿠키.
  HTML 폼은 다른 사이트에서 `application/json`을 보낼 수 없습니다.
- 별도의 CSRF 토큰은 쓰지 않습니다. 화면을 구현할 때 같은 출처에서 `fetch`로 호출하면 그대로 동작합니다.
- 주의: 리버스 프록시가 `Host` 헤더를 바꾸는 배포에서는 `Origin` 비교가 실패할 수 있습니다.
  그 경우 신뢰할 출처를 `AddTrustedOrigin`으로 등록하는 설정이 필요합니다. (현재 미구현)

### 2.9 등록 기능의 알려진 한계

이번 범위에서 해결하지 않고 기록만 합니다.

- **응답 유실**: 새 등록이 커밋됐지만 응답이 브라우저에 도착하지 않으면 쿠키도 저장되지 않습니다.
  - 쿠키가 없던 경우: 같은 이메일로 다시 등록하면 409가 되고, 이메일만으로는 기존 팀에 접근할 수 없으므로 그 팀을 복원할 방법이 없습니다. 그 팀은 대기열에 남습니다.
  - 완료 쿠키로 재등록한 경우: 브라우저에는 이전 완료 팀의 쿠키가 남습니다. 이 쿠키는 `successorId`를 통해 새 팀으로 연결되므로,
    새 팀이 진행 중인 동안에는 다시 요청하면 200으로 새 팀을 돌려줍니다. 새 팀의 쿠키는 발급되지 않습니다.
    (토큰 원문을 저장하지 않으므로 재발급 불가. 토큰 회전은 동시 응답의 쿠키를 무효로 만들 수 있어 하지 않음)
- **오래된 완료 쿠키**: 연결은 한 단계만 따라갑니다. 재등록한 새 팀까지 완료된 뒤 첫 완료 쿠키를 보내면 **쿠키가 없는 요청과 같이** 처리합니다.
  - 진행 중인 다른 팀의 이메일이면 409, 사용 가능한 이메일이면 새 팀 201(새 쿠키 발급)
  - 첫 완료 팀의 `successorId`는 처음 재등록한 팀을 계속 가리키고, 새로 연결하지 않습니다.
  - 이 경우에는 완료 쿠키당 재등록 한 건 보장이 적용되지 않습니다. 이메일이 서로 다른 동시 요청은 여러 건이 될 수 있습니다.
  - 정상 흐름(201 응답이 도착함)에서는 브라우저가 가장 최근 팀의 쿠키를 갖고 있으므로 이 경우가 생기지 않습니다.
    이 상황은 재등록 응답이 유실되고 그 팀까지 완료된 뒤에만 생깁니다.
- **다른 이메일로 여러 번 등록**: 쿠키가 없는 브라우저나 다른 브라우저에서 이메일을 바꿔 등록하는 것은 식별할 수 없습니다. (2.1의 정책)
- **진행 중 쿠키로 다른 입력**: 입력을 무시하고 기존 팀을 돌려줍니다. 등록 정보 수정 기능은 없습니다.
- **잘못된 쿠키 정리**: 알 수 없는 토큰 쿠키를 삭제하는 응답은 보내지 않습니다. 새 등록에 성공하면 새 쿠키로 덮어씁니다.
- **오래된 쿠키의 조회 결과**: 재등록 응답이 유실되고 successor까지 완료된 뒤 다시 등록해 새 팀을 만들면,
  새 팀은 새 쿠키로만 조회됩니다. 그 응답까지 유실되면 브라우저의 오래된 쿠키는 계속 이전 successor의 완료 상태를 보여 줍니다.
- **경합 시 지연**: 모든 등록이 식당 문서를 갱신하므로 동시 등록은 쓰기 충돌 재시도로 직렬화됩니다. 학습용 규모에서는 문제가 없지만 대량 동시 요청에서는 지연이 늘 수 있습니다.

## 3. 미정 사항

구현 전에 결정해야 하는 세부 사항입니다. 아래 항목은 새 기능이나 운영 정책이 아니라, 위 정책을 구현하는 방법에 대한 선택입니다.

> 등록 API 구현으로 결정된 항목(필드명, 인덱스, 순번 발급, 이메일 중복 방지, 토큰·해시, 트랜잭션 재시도와
> 제한 시간, read/write concern, 쿠키 속성, CSRF, 이메일 형식, 이름 길이)은 2.4~2.8로 옮겼습니다.

### 데이터

- 완료된 팀 문서의 보관 여부
- 체크인·종료 시 쓸 인덱스 (예: 대기 중 팀의 순번 순 조회, 종료 시각 조회)

### 동시성

- 체크인·식사 종료 트랜잭션의 세부 조건 (등록과 같은 재시도·제한 시간 헬퍼 재사용 예정)

### 식사 종료 작업

- 확인 주기
- 한 번에 처리할 팀 수, 팀별 개별 트랜잭션 여부
- 서버 인스턴스가 여러 개일 경우의 중복 실행 처리 (현재는 단일 인스턴스 전제. 조건부 갱신으로 중복 반환은 막아야 함)

### 화면·API

- HTML 화면 경로, API 응답 형식과 오류 코드
- 폴링 간격 최종값, 폴링 중 오류·네트워크 끊김 시 표시
- 남은 시간 표시 시 서버·클라이언트 시계 차이 처리 (예: 서버가 남은 시간이나 서버 시각을 함께 제공)
- 체크인 버튼을 폼 제출로 할지 JavaScript 요청으로 할지, JavaScript가 없을 때의 동작
- 원문의 프런트엔드 패턴 중 어느 것으로 설명할지 (SSR + 부분 JavaScript는 "Pure SSR/no interactivity"보다 "Islands"에 가까움)
- 쿠키에 진행 중인 팀이 연결된 상태에서 **등록 화면**에 접근할 때의 화면 처리
  (API는 결정됨: 다른 이메일로 등록해도 기존 팀을 200으로 반환)
- 리버스 프록시 뒤 배포 시 신뢰 출처(`AddTrustedOrigin`) 설정

### 실행 환경

- Docker Compose에서 MongoDB replica set 초기화 방법(초기화 시점, 멤버 호스트 이름이 앱 컨테이너에서 접근 가능해야 함)
- 앱이 MongoDB 준비 완료를 기다리는 방법
- Playwright 테스트를 Compose 안에서 실행할지 여부
