이 문서는 세 부분으로 나뉩니다.

1. **원문 필수 요구사항** — [`README.md`](../README.md)(과제 원문)에서 확인한 내용
2. **자체 설계 결정** — 원문을 해석해 이 프로젝트가 선택한 정책과 설계

> "초안"으로 표시한 부분은 구현 과정에서 바뀔 수 있습니다.

## 1. 원문 필수 요구사항

원문 README에서 확인한 요구사항입니다. 아래 표현은 원문을 요약한 것이며, 해석은 2장에서 다룹니다.

### 기술 요구사항

| 항목 | 원문 요구사항 |
| --- | --- |
| 실행 | 전체 앱이 로컬에서 `docker compose up`으로 실행되어야 함 |
| 프런트엔드 패턴 | Isomorphic SSR / Pure SSR(상호작용 없음) / Islands 중 하나. **SPA 금지** |
| 프런트엔드 구현 | 의존성 없는 순수 vanilla JS 또는 React v18+ |
| 백엔드 | Ruby on Rails / Node.js(next·nest 제외) / Go(프레임워크 무관) 중 하나 |
| E2E 테스트 | Playwright |
| 데이터베이스 | MongoDB |

### 비즈니스 요구사항

- **식당 정원**: 10석으로 고정
- **식사 시간**: 인원당 3초로 고정 (예: 4명이면 12초)
- **대기 등록**: 이름(Name), 이메일(Email), 인원수(Party size) 세 필드가 있는 단일 폼. 제출 시 대기 등록 API 요청을 보냄
- **체크인**: 대기 중인 팀이 입장할 준비가 되면 앱에 "check in" 버튼을 표시. 클릭하면
  - 해당 팀이 대기열에서 제외되고
  - 사용 가능한 좌석이 인원수만큼 줄고
  - 해당 팀의 식사 카운트다운이 시작됨
- **상태 확인**: 사용자는 **여러 브라우저 세션에 걸쳐** 자신의 대기 상태를 볼 수 있어야 함
- **대기열 관리**: 한 팀의 식사가 끝나면
  - 시스템이 대기열에서 다음 팀을 확인하고
  - 다음 팀의 인원수만큼 좌석이 있으면 그 팀의 앱에 체크인 버튼을 표시하며
  - 좌석이 부족하면 충분해질 때까지 기다림
- **중복 등록**: 한 팀이 대기열에 두 번 나타나면 안 됨
- **동시성**: 두 팀이 동시에 등록하려 해도 식당이 초과 예약되면 안 되며, 각 팀에 최선의 경험을 제공해야 함

### 제출 요구사항

- 공개 GitHub 저장소
- 원문 README를 포함하고, 로컬 설정·실행 방법을 명확히 안내
- 아키텍처 결정에 대한 간단한 설명(README 또는 별도 문서)

## 2. 자체 설계 결정

### 2.1 운영 정책

#### 좌석과 식사 시간

- 테이블 구분 없이 **총 10석**을 하나의 좌석 풀로 관리합니다.
- 식사 시간은 **인원당 3초**입니다. 식사 종료 예정 시각 = 체크인 시각 + 인원수 × 3초.

#### 입장 순서

- **등록 순서대로** 입장합니다.
- 맨 앞 팀이 입장할 만큼 좌석이 없으면 **뒤 팀도 함께 기다립니다.**
  좌석이 남아 있더라도 뒤 팀이 앞 팀을 건너뛰어 입장하지 않습니다.
- 앞 팀이 체크인하면 그다음 팀의 입장 가능 여부를 확인합니다.
- 따라서 "체크인 가능"한 팀은 대기 중인 팀 가운데 맨 앞 팀이며, 그 팀의 인원수가 남은 좌석 수 이하일 때입니다.

#### 체크인하지 않는 팀

- 체크인 제한 시간과 자동 취소는 **구현하지 않습니다.**
- **알려진 한계**: 맨 앞 팀이 체크인 가능 상태에서 체크인하지 않으면 대기열 전체가 막힐 수 있습니다.
  이 한계는 기록만 하고 구현 범위에서는 제외합니다.

#### 팀 식별과 중복 등록

- **이메일**을 팀 대표자의 식별 기준으로 사용합니다.
- 중복 비교 시 이메일의 **앞뒤 공백을 제거하고 대소문자를 통일**합니다.
- 같은 이메일로 **대기 중 · 체크인 가능 · 식사 중**인 팀이 있으면 추가 등록을 막습니다.
- **이용 완료** 후에는 같은 이메일로 새로 등록할 수 있습니다.
- 같은 팀이 **다른 이메일**로 등록하는 경우는 주어진 정보(이름·이메일·인원수)로 식별할 수 없으므로 막지 않습니다.
  원문의 "한 팀이 대기열에 두 번 나타나면 안 됨"은 "같은 이메일의 진행 중인 팀은 하나뿐"으로 해석합니다.

#### 인원수

- 한 팀은 **1~10명의 정수**만 허용합니다. (정원보다 큰 팀은 영원히 입장할 수 없으므로 거부)
- 팀을 나누어 등록하는 기능은 추가하지 않습니다.

### 2.2 상태 복원 (여러 브라우저 세션)

원문의 "여러 브라우저 세션에 걸쳐 상태를 볼 수 있어야 함"을 다음 범위로 해석해 선택했습니다.

**지원 범위**

- **같은 브라우저**에서의 새로고침, 재방문, 브라우저 종료 후 재접속

**방식**

- 등록 시 추측하기 어려운 무작위 식별 토큰을 발급해 **유지되는(persistent) 쿠키**에 보관합니다.
- 서버는 요청의 토큰으로 연결된 팀을 찾아 **최신 상태를 DB에서 조회**합니다.
- DB에는 토큰 원문 대신 **검증용 해시**를 저장하는 방향으로 설계합니다.

**제외 범위**

- 로그인
- 다른 브라우저·다른 기기에서의 복원
- 쿠키 삭제 후 복원

이는 원문을 해석해 선택한 범위이며, 원문이 다른 브라우저·기기 간 복원까지 의도했을 가능성은 남아 있습니다.

### 2.3 화면

SSR로 생성하는 두 화면으로 구성합니다.

#### 등록 화면

- 이름 · 이메일 · 인원수 입력, 등록 버튼
- 입력 오류 안내 (필수값 누락, 이메일 형식, 인원수 범위, 진행 중인 같은 이메일 등)

#### 내 상태 화면

상태에 따라 표시가 바뀝니다.

| 상태 | 표시 |
| --- | --- |
| 대기 중 | 내 앞에 남은 **대기 팀 수** |
| 체크인 가능 | 입장 안내와 **체크인 버튼** |
| 식사 중 | 서버의 **식사 종료 예정 시각**을 기준으로 계산한 남은 시간 |
| 이용 완료 | 완료 안내와 **다시 등록**할 수 있는 경로 |

- 앞 팀 수는 **대기 중인 팀만** 셉니다. 체크인한 팀은 대기열과 앞 팀 수에서 제외합니다.
- **예상 대기 시간은 제공하지 않습니다.** 미응답 팀 자동 취소가 없어 앞 팀의 체크인 지연을 예측할 수 없기 때문입니다.
- 내 상태 화면은 **폴링 방식**으로 자동 갱신합니다.
  - 폴링 간격 **1초는 초기 제안값**이며 최종 확정값이 아닙니다.
- 브라우저에서 버튼을 숨기거나 비활성화하는 것만으로 중복·동시 요청을 막았다고 간주하지 않습니다.
  모든 규칙은 서버와 DB에서 다시 검사합니다.

### 2.4 데이터 설계 (초안)

팀별 문서와 식당 문서를 분리합니다. **구체적인 필드명·인덱스·순번 발급 방식은 아직 초안입니다.**

#### 팀 문서 (예: `parties` 컬렉션)

| 필요한 정보 | 비고 |
| --- | --- |
| 등록 정보 | 이름, 이메일(입력값과 정규화 값), 인원수 |
| 등록 순번 | 입장 순서 판단 기준. 단조 증가해야 함 |
| 상태 | 저장하는 값은 **대기 중 · 식사 중 · 완료** 세 가지 |
| 체크인 시각 | 식사 중 이후 |
| 식사 종료 예정 시각 | 체크인 시 서버가 계산해 저장 |
| 식별 토큰 검증값 | 토큰 원문이 아닌 해시 |

#### 식당 문서 (예: `restaurants` 컬렉션, 단일 문서)

| 필요한 정보 | 비고 |
| --- | --- |
| 정원 | 10 |
| 사용 중인 좌석 수 | 항상 0~10 |

#### 저장하지 않고 계산하는 값

- **체크인 가능 여부**: 대기 중 + 대기 중인 팀 중 맨 앞 + 인원수 ≤ (정원 − 사용 중인 좌석)
- **앞 팀 수**: 나보다 등록 순번이 앞선 대기 중인 팀의 수
- **남은 식사 시간**: 식사 종료 예정 시각 − 현재 서버 시각

### 2.5 동시 요청과 체크인

#### 체크인 처리

- 체크인 요청 시 서버가 다음을 **다시 확인**합니다.
  - 팀의 현재 상태
  - 대기 순서(맨 앞 팀인지)
  - 빈 좌석 수
- 팀 상태 변경(대기 중 → 식사 중)과 식당 좌석 변경(사용 중 좌석 + 인원수)을 **하나의 MongoDB 트랜잭션**으로 묶습니다.

#### 트랜잭션에 대한 주의

트랜잭션을 사용한다고 자동으로 안전해지지는 않습니다. 다음이 함께 필요합니다.

- **공통 식당 문서 갱신**: 좌석에 영향을 주는 모든 트랜잭션(체크인, 식사 종료)이 같은 식당 문서를 쓰도록 해,
  동시에 진행된 트랜잭션끼리 쓰기 충돌이 나게 만듭니다. 서로 다른 문서만 읽고 쓰면 각자 오래된 값을 근거로
  판단한 결과가 모두 커밋될 수 있습니다.
- **충돌 재시도**: 쓰기 충돌 등 일시적 트랜잭션 오류가 나면 트랜잭션 전체를 다시 실행합니다.
- **재시도 시 조건 재확인**: 재시도할 때 이전 시도에서 읽은 값을 재사용하지 않고, 상태·순서·좌석 조건을 처음부터 다시 확인합니다.
- 좌석 갱신 자체도 조건부로 수행합니다(예: 사용 중 좌석 + 인원수 ≤ 정원일 때만 증가).

#### 지켜야 할 불변 조건

- 사용 중인 좌석은 **항상 0~10석**입니다.
- 좌석 차감과 반환은 **팀별로 각각 한 번만** 반영됩니다.
- **반복 체크인**으로 좌석을 다시 차감하지 않습니다. 이미 체크인된(식사 중인) 팀의 재요청에는 **현재 상태를 반환**합니다.
- **완료된 팀**의 체크인 요청으로 식사를 다시 시작하지 않습니다.

#### 동시 등록

- 진행 중(대기 중·식사 중)인 같은 정규화 이메일의 동시 등록은 애플리케이션 검사뿐 아니라 **DB 수준에서도** 막습니다
  (구체적인 방식은 3장 참고).

#### 로컬 MongoDB 구성

- MongoDB 트랜잭션은 replica set(또는 sharded cluster)에서만 동작하므로,
  로컬 Docker Compose 환경도 **replica set으로 구성**해야 합니다.

### 2.6 식사 종료

- **서버 내부의 주기적 작업**이 식사 종료 예정 시각이 지난 팀을 확인합니다.
- 팀 상태 변경(식사 중 → 완료)과 좌석 반환을 **하나의 트랜잭션**으로 묶습니다.
- 이미 완료한 팀은 다시 좌석을 반환하지 않습니다(상태가 식사 중일 때만 완료 처리).
- 브라우저 접속이나 상태 조회 요청이 **없어도** 종료 처리가 동작합니다.
- 서버 재시작 후에는 **DB에 저장된 종료 예정 시각**을 기준으로 처리를 재개합니다.
  메모리의 타이머에 의존하지 않으므로 재시작 중 종료 시각이 지난 팀도 다음 확인에서 처리됩니다.
- **처리 지연**: 주기적으로 확인하므로 실제 완료 처리는 종료 예정 시각보다 최대 "확인 주기 + 처리 시간"만큼 늦을 수 있습니다.
  이 동안 좌석은 아직 반환되지 않은 상태로 보이며, 다음 팀의 체크인 가능 표시도 그만큼 늦어질 수 있습니다.
- 손님용 식사 종료 버튼이나 종료 API는 추가하지 않습니다.

### 2.7 API 초안

> 아래 경로와 응답 형식은 **초안이며 아직 구현되지 않았습니다.**

| 메서드 | 경로 | 용도 |
| --- | --- | --- |
| `POST` | `/api/parties` | 대기 등록 (이용 완료 후 재등록도 같은 경로 사용) |
| `GET` | `/api/me` | 쿠키의 토큰에 연결된 내 팀의 상태 조회 |
| `POST` | `/api/me/check-in` | 체크인 |

- HTML 화면(등록 화면, 내 상태 화면)을 제공하는 경로는 API와 별도로 둡니다. 구체적인 경로는 미정입니다.
- 상세 요청·응답 형식과 오류 코드는 미정입니다.

## 3. 미정 사항

구현 전에 결정해야 하는 세부 사항입니다. 아래 항목은 새 기능이나 운영 정책이 아니라, 위 정책을 구현하는 방법에 대한 선택입니다.

### 데이터

- 필드명, 상태 값 표기, 인덱스 구성
- **등록 순번 발급 방식**: 예) 카운터 문서를 원자적으로 증가 / 다른 단조 증가 값. 여러 요청이 동시에 와도 순번이 겹치거나 역전되지 않아야 함
- **진행 중 이메일의 DB 수준 중복 방지 방식**: 예) 상태 조건을 건 partial unique index /
  진행 중일 때만 값이 있는 별도 필드에 unique index 등. 사용할 MongoDB 버전의 partial index 지원 범위 확인 필요
- 토큰 길이와 해시 알고리즘 (무작위 고엔트로피 토큰이므로 빠른 해시로 충분한지 확인)
- 완료된 팀 문서의 보관 여부

### 동시성

- 트랜잭션 재시도 방식(드라이버의 재시도 헬퍼 사용 여부)과 재시도 횟수·시간 상한
- 트랜잭션 read/write concern
- 등록 트랜잭션이 식당 문서를 함께 갱신해야 하는지 여부 (순번 발급 방식과 연관)

### 식사 종료 작업

- 확인 주기
- 한 번에 처리할 팀 수, 팀별 개별 트랜잭션 여부
- 서버 인스턴스가 여러 개일 경우의 중복 실행 처리 (현재는 단일 인스턴스 전제. 조건부 갱신으로 중복 반환은 막아야 함)

### 화면·API

- HTML 화면 경로, API 응답 형식과 오류 코드
- 폴링 간격 최종값, 폴링 중 오류·네트워크 끊김 시 표시
- 남은 시간 표시 시 서버·클라이언트 시계 차이 처리 (예: 서버가 남은 시간이나 서버 시각을 함께 제공)
- 체크인 버튼을 폼 제출로 할지 JavaScript 요청으로 할지, JavaScript가 없을 때의 동작
- 원문의 프런트엔드 패턴 중 어느 것으로 설명할지 (SSR + 부분 JavaScript는 "Pure SSR/no interactivity"보다 "Islands"에 가까움)
- 쿠키 속성(HttpOnly, SameSite, Secure, 만료 기간)과 POST 요청의 CSRF 대응
- 쿠키에 진행 중인 팀이 연결된 상태에서 등록 화면에 접근하거나 다른 이메일로 등록할 때의 처리
- 이메일 형식 검증 규칙, 이름 길이 제한

### 실행 환경

- Docker Compose에서 MongoDB replica set 초기화 방법(초기화 시점, 멤버 호스트 이름이 앱 컨테이너에서 접근 가능해야 함)
- 앱이 MongoDB 준비 완료를 기다리는 방법
- Playwright 테스트를 Compose 안에서 실행할지 여부
